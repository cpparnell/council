# BTC LLM Council Trading Bot — System Specification

## Overview

A Bitcoin swing trading bot that uses a council of specialised LLM agents to make daily trading decisions. The system combines quantitative signal generation (technical indicators) with qualitative reasoning (news, sentiment, on-chain context) and a structured multi-agent deliberation process. The council operates once per day (but should be built to allow a change in this frequency), producing a BUY / SELL / HOLD signal with position size and stop loss attached.

This is not a high-frequency trading system. The LLM edge is in narrative synthesis — weighing macro context, news flow, on-chain data, and sentiment into a coherent directional view over a 24–72 hour horizon.

---

## Asset

**BTC/USD** (primary).

Reasons: deepest liquidity, richest data ecosystem (on-chain metrics, social sentiment, news), 24/7 market, well-studied in LLM trading research, no overnight gap risk.

Exchange: **Binance** or **Hyperliquid** (both have robust Python APIs and sandbox environments).

---

## Trading Cadence

| Mode | Cycles/day | Est. monthly cost (full council) |
|---|---|---|
| Development / testing | 1 (daily close) | ~$30 |
| Production | 1–6 (daily or 4-hour) | ~$30–$180 |

Start at **daily cadence** during development. One council meeting per day at a fixed time (e.g. 00:00 UTC on the daily close). Move to 4-hour cycles only after signal quality is validated through paper trading.

At this frequency, the tiered cost-reduction architecture is **not required** — run the full council every cycle. The system stays simple.

## Architecture Overview

```
Data Pipeline
    │
    ├── Price data       (OHLCV + indicators via CCXT / Binance API)
    ├── News feed        (crypto + macro via NewsAPI / CryptoPanic)
    ├── Social data      (X/Reddit sentiment via LunarCrush or Nitter)
    └── On-chain metrics (whale flows, exchange inflows via Glassnode / CryptoQuant)
    │
    ▼
Tier 0: Rules Engine  ← free, runs every cycle, validates data + computes indicators
    │
    ▼
Council of LLMs  ← runs in parallel, each agent gets the same structured context
    ├── Technical analyst agent
    ├── Sentiment analyst agent
    ├── Fundamental analyst agent
    └── Risk manager agent
    │
    ▼
Bull vs. Bear deliberation  ← synthesis model weighs agent outputs
    │
    ▼
Consensus + veto gate  ← risk manager can block any signal
    │
    ▼
Signal: BUY / SELL / HOLD + position size + stop loss
    │
    ▼
Execution layer  ← Binance / Hyperliquid API
    │
    └── Reflection loop: log outcome, feed back into next cycle context
```

### Data validation (Tier 0 — runs before any LLM call)

- Reject cycle if price data is stale (> 5 minutes old)
- Reject cycle if fewer than 10 news items retrieved
- Validate all numeric fields are non-null and within plausible range
- Log validation failures; default to HOLD on any hard failure

## The Council

### Agent roles

Four agents run in parallel. Each receives the full context object and returns a structured JSON response.

#### 1. Technical analyst

**System prompt focus:** Chart patterns, indicator alignment, trend structure, support/resistance levels. Quantitative reasoning only — no opinion on news or macro.

**Output schema:**
```json
{
  "direction": "BUY | SELL | HOLD",
  "confidence": 0-100,
  "timeframe": "24h | 48h | 72h",
  "key_signals": ["RSI oversold bounce", "EMA 20/50 bullish cross"],
  "invalidation_level": 81000
}
```

#### 2. Sentiment analyst

**System prompt focus:** News tone, social mood, narrative shifts. Identify the dominant market story of the last 24h. Flag any high-impact events (regulatory news, exchange hacks, ETF flows, macro surprises).

**Output schema:**
```json
{
  "direction": "BUY | SELL | HOLD",
  "confidence": 0-100,
  "overall_sentiment": "bullish | bearish | neutral | mixed",
  "dominant_narrative": "...",
  "high_impact_events": ["..."],
  "sentiment_vs_price_divergence": true
}
```

#### 3. Fundamental analyst

**System prompt focus:** On-chain health, macro backdrop, structural supply/demand. Exchange outflows (bullish) vs inflows (bearish). SOPR above/below 1. Whale accumulation vs distribution.

**Output schema:**
```json
{
  "direction": "BUY | SELL | HOLD",
  "confidence": 0-100,
  "onchain_bias": "accumulation | distribution | neutral",
  "macro_bias": "risk-on | risk-off | neutral",
  "key_factors": ["Exchange outflows accelerating", "SOPR > 1 suggests profit-taking"]
}
```

#### 4. Risk manager

**System prompt focus:** Portfolio risk, not market direction. Evaluate the proposed trade against current drawdown, position sizing rules, and volatility. The risk manager does NOT give a market view — it approves or vetoes based on risk parameters.

**Hard rules (non-negotiable, enforced in code before agent call):**
- Max position size: 20% of portfolio per trade
- Max single-trade risk: 2% of portfolio (stop loss sized accordingly)
- Max drawdown halt: if portfolio is down >15% from peak, no new trades
- No trading during extreme volatility (ATR > 2× 30-day average)

**Output schema:**
```json
{
  "veto": false,
  "veto_reason": null,
  "approved_position_size_pct": 15,
  "recommended_stop_loss": 80200,
  "recommended_take_profit": 88000,
  "risk_reward_ratio": 2.1,
  "notes": "..."
}
```

## Deliberation Layer

After the four agents return their outputs, a deliberation model (Claude Sonnet or GPT-4o) synthesises them into a final decision. This is the "bull vs. bear debate" step.

### Deliberation prompt structure

```
You are the chair of a trading committee. Four specialist agents have analysed the market.
Here are their reports: [agent outputs as JSON]

Your job:
1. Identify where agents agree and where they conflict.
2. Weigh the disagreements — which agent's domain is most relevant right now?
3. Produce a final synthesised signal.
4. If the risk manager has vetoed, output HOLD regardless.

Return only valid JSON matching this schema:
{
  "final_signal": "BUY | SELL | HOLD",
  "conviction": "high | medium | low",
  "consensus_summary": "...",
  "key_disagreements": ["..."],
  "agent_weights_applied": {
    "technical": 0.30,
    "sentiment": 0.25,
    "fundamental": 0.30,
    "risk": 0.15
  }
}
```

### Consensus rules

| Condition | Outcome |
|---|---|
| Risk manager veto | HOLD — overrides everything |
| All 3 directional agents agree, avg confidence ≥ 70 | Execute signal |
| 2 of 3 agree, avg confidence ≥ 60 | Execute with reduced position size (50%) |
| Split or avg confidence < 60 | HOLD |
| Deliberation model fails or times out | HOLD |

Default to HOLD on any ambiguity. Missing a trade is cheap. A bad trade is expensive.

## Execution Layer

### Order logic

On a BUY signal:
1. Calculate position size from risk manager output
2. Place market buy order via exchange API
3. Immediately place stop-loss order (OCO or stop-limit)
4. Optionally place take-profit limit order
5. Log full context, agent outputs, deliberation, and order details

On a SELL signal:
1. If currently holding BTC: close position at market
2. Optionally open short (only if explicitly configured — disabled by default)

On HOLD:
1. Log cycle, no order placed
2. If currently holding a position, existing stop-loss remains active

### State management

Maintain a simple SQLite database tracking:
- Current position (size, entry price, entry timestamp)
- All past trades (entry, exit, PnL)
- All cycle logs (context snapshot, agent outputs, final signal)
- Portfolio peak value (for drawdown calculation)

### Error handling

- Wrap all exchange API calls in try/except with retry (max 3 attempts, exponential backoff)
- On order failure: log error, do NOT retry trade logic, alert via Telegram/email
- On partial fill: log warning, adjust position tracking accordingly
- Reconcile expected vs actual positions at the start of every cycle

## Risk Management (Hard Rules)

These are enforced in Python code, not by LLMs. No agent output can override them.

```python
MAX_POSITION_SIZE_PCT = 0.20      # max 20% of portfolio in one trade
MAX_TRADE_RISK_PCT    = 0.02      # max 2% of portfolio lost if stop hit
MAX_DRAWDOWN_HALT_PCT = 0.15      # halt all trading if down >15% from peak
MAX_ATR_MULTIPLIER    = 2.0       # no trades if ATR > 2× 30-day average ATR
MIN_RISK_REWARD       = 1.5       # only take trades with R:R ≥ 1.5
```

Stop loss sizing formula:
```
position_size = (portfolio_value × MAX_TRADE_RISK_PCT) / (entry_price - stop_loss_price)
```

## Reflection Loop

After each completed trade (position closed), run a reflection step:

1. Feed the original council outputs and the trade outcome (profit/loss) to a reflection model
2. Ask: "Given the outcome, which agent's view was most predictive? Was the veto logic appropriate? What would improve the next decision?"
3. Store the reflection summary in the cycle log
4. Optionally surface recurring patterns to a weekly summary report

This does not dynamically alter agent weights (avoid overfitting a handful of trades). Use it for human review and prompt refinement.

## Key Challenges to Mitigate in Implementation

### 1. Lookahead bias in backtesting
- Use walk-forward optimisation only — train on window A, test on window B, never overlap
- Validate all indicator calculations use only data available at decision time
- Use `vectorbt` or `backtrader` with strict time-series discipline

### 2. LLM hallucination on market data
- Always pass numeric data as structured JSON, not narrative descriptions
- Validate all agent outputs against strict JSON schemas before use
- Never pass raw agent text directly to the order router — always parse and validate first

### 3. Regime change
- Include a simple regime classifier in Tier 0 (trending vs ranging vs high-volatility) using ADX + ATR
- Include the current regime label in the context object so agents are aware
- Consider reducing position size or defaulting to HOLD during undefined/crisis regimes

### 4. Prompt sensitivity
- Version-control all system prompts in a `prompts/` directory
- Never edit prompts while live — test changes on paper trading first
- Log which prompt version produced each trade decision

| Agent | Model | Rationale |
|---|---|---|
| Technical analyst | `claude-haiku-4-5` | Fast, cheap, structured output |
| Sentiment analyst | `deepseek-v3` | Strong sentiment reasoning, low cost |
| Fundamental analyst | `gemini-2.0-flash` | Good at structured data synthesis |

| Deliberation / chair | `claude-sonnet-4-6` | Best chain-of-thought synthesis |

All models must be called with `temperature=0` or equivalent for deterministic, conservative outputs.

## Development Phases

### Phase 1 — Data pipeline + Tier 0
- Set up CCXT connection to Binance testnet
- Build context object assembler (price + indicators + news + on-chain)
- Implement data validation and hard risk rules
- Unit test all indicator calculations

### Phase 2 — Agent framework
- Implement each agent with its system prompt and output schema
- Build Pydantic validation models for all agent outputs
- Run agents in parallel with `asyncio.gather()`
- Test with static context objects before connecting live data

### Phase 3 — Deliberation + execution
- Implement deliberation model and consensus logic
- Build order execution layer against Binance testnet
- Implement SQLite logging

### Phase 4 — Paper trading
- Run full system on live data with simulated capital for minimum 60 days
- Review every cycle log weekly
- Refine prompts based on reflection summaries

### Phase 5 — Live deployment
- Deploy with minimal capital (≤ $500) for first 30 days
- Scale up only after live performance matches paper trading results

## What Success Looks Like

Do not optimise for win rate. Optimise for:
- **Sharpe ratio ≥ 1.5** (risk-adjusted returns)
- **Max drawdown < 20%**
- **Positive expectancy** (average winning trade × win rate > average losing trade × loss rate)
- **Council consistency** — agents should not wildly disagree on obvious market conditions

A system that HOLDs 80% of the time and only trades on genuine high-conviction signals is the target behaviour. Overtrading is the enemy.
